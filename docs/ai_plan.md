# 注意股專題：AI 可以做什麼

> 2026-11-16 整理，2026-11-21 更新

資料線（API → raw → stage → app）已經完成。往上加三個 AI 項目，三個都要做；各自讀資料庫、各自寫結果表，哪一個當天失敗都不影響資料線和網站。最後串進排程、網站、雲端。

## 整體架構

### 現況：資料已經準備好

| 層 | 內容 |
| --- | --- |
| crawler | 證交所 7 個 API、觀測站重大訊息和全文 → 9 張 raw 表，每天 21:00 自動跑 |
| transform | 款次解析、民國轉西元、交易日曆、收盤行情、重大訊息全文 → 13 張 stage 表 |
| analyze | 規則引擎（要點第六條）：還差幾次、若再列注意的處置日期、出關日 → 2 張 app 表＋網頁用的 VIEW；回測 75 筆真實處置全對 |

給 AI 用的資料：

- **重大訊息全文** 7,391 則（2026/04/01 起，每天增加），每則有符合條款、事實發生日、說明全文（平均約 570 字）。
- **條款對照表**：重大訊息第 4 條第 1～51 款各代表什麼（固定資料）。
- **規則條文**：注意交易資訊公告及處置作業要點。
- **新聞**：FinMind 的 `TaiwanStockNews`，每檔每天的新聞標題、連結、來源、時間。

### 架構圖

```
資料線（已完成）
  證交所、觀測站 API → crawler → raw → transform → stage → analyze → app

AI 三個項目（只讀 stage、app 表，結果寫進 ai_* 表）
  ├─ ① 公告分類
  │     LLM（小型模型）結構化輸出
  │     → ai_announcement_label
  ├─ ② 新聞 RAG（給 ③ 用）
  │     FinMind 新聞 → raw_stock_news → stage_news、stage_stock_news；新聞網頁 → raw_news_detail（只存 <head>）→ stage_news_detail
  │     標題轉成向量（embedding）存進 PostgreSQL（pgvector）→ ai_news_embedding
  │     向量檢索：同一件事的報導合併成一則，再挑跟「被注意的原因、公告」最相關的幾則，交給 ③ 的 LLM
  └─ ③ 卡片 AI 摘要（用 ① 的標籤、② 的新聞）
        程式查好自己的資料（app_card、公告）＋ ① 的標籤 ＋ ② 的新聞 → LLM 寫 2～3 句白話
        → ai_card_summary（新聞那句附出處）

網站
  資料 API（FastAPI）讀 app_*、ai_* 表，Streamlit 網頁打 API（Airflow 每天收盤後跑）
```

### 三個項目一覽

| 項目 | 做什麼 | 為什麼要做 | 結果 | 必做 |
| --- | --- | --- | --- | --- |
| ① 公告分類 | 判斷每則公告的類型（13 類）、是不是更正、有沒有新消息，再寫一句白話摘要 | 現在用主旨關鍵字判斷，錯很多；官方條款太粗（第51款什麼都有） | 公告類型標籤、白話摘要 | 必做 |
| ② 新聞 RAG | 抓 FinMind 新聞，跟自己的資料一起交給 ③ 寫摘要 | 只看公告不知道市場在討論什麼 | 摘要多一句新聞，附出處連結 | 必做 |
| ③ 每日卡片 AI 摘要 | 替每檔注意股、聽牌股寫 2～3 句白話 | 款次、原因是法規寫法，一般人看不懂 | 卡片最上面的摘要 | 必做 |

三個都要做，而且一起做：①＋②＋③ → 串起來、上雲。① 的標籤和 ② 的新聞都是 ③ 的輸入，所以 ③ 一開始就把公告標籤和新聞一起帶進去，不分兩階段。實際動手時，① 和 ② 的抓新聞可以同時開工，③ 先用手邊有的資料寫，①、② 好了就接上；② 哪天抓不到新聞，③ 照樣只用自己的資料寫。

每個項目多學一個新概念：

| 項目 | 新概念 | AI 的角色 | 誰找資料 |
| --- | --- | --- | --- |
| ① | 結構化輸出 | 照固定格式回答問題 | 程式直接給 |
| ② | embedding、向量檢索（pgvector）、引用來源 | （不用 LLM）用意思合併重複的報導、挑出相關的新聞 | 向量資料庫（PostgreSQL＋pgvector） |
| ③ | RAG 的生成 | 把查好的資料寫成人話 | 程式用 SQL 查 |

② 加 ③ 就是完整的 RAG：檢索（自己的資料用 SQL 查、新聞用向量找）＋生成（寫成摘要、附出處）。

### 共同原則

- AI 全部在每天收盤後批次執行，結果存成表給卡片網站讀；不做聊天式問答。
- 還差幾次、處置日期仍由規則引擎計算，AI 不取代它。
- AI 結果放獨立的 `ai_*` 表：重跑要花錢、答案每次可能不同，所以拿到就留著，不跟可以隨時重算的 `app_*` 混在一起。
- 每個項目只處理新資料：每則公告只分類一次，之後每天只處理新進來的。

## ① 公告分類

**做什麼**：替每則重大訊息判斷三件事：公告類型（13 類選一個）、是不是更正／補充、有沒有新消息；再寫一句白話摘要。

**為什麼要做**：現在用主旨關鍵字判斷公告類型，錯很多：

| 關鍵字規則的問題 | 例子 |
| --- | --- |
| 誤判成說明 | 「受邀參加線上法說會，說明115年第一季營運成果」：是法說會，不是事件說明 |
| 漏掉回應媒體 | 「媒體報導本公司遭彰化縣衛生局處罰新台幣600萬」：沒有「澄清」「說明」字樣 |
| 漏掉更正類 | 「（補充說明）本公司油品代製廠商…」：規則只認「更正」 |

官方的「符合條款」也幫不上忙：第51款「其他重大事項」有 1,303 則，什麼都有（注意股例行說明、澄清媒體、營收、新藥許可…）。
要判斷「是不是回應媒體」「有沒有新消息」得讀懂意思，關鍵字和條款都做不到，所以交給 AI。

**分類**：

1. **類型**（選一個），比條款細、用白話：

| 類型 | 例子 |
| --- | --- |
| 注意股例行說明 | 「係因本公司有價證券達公布注意交易資訊標準，故公布相關財務業務等重大訊息」（依規定公布，通常沒有新消息） |
| 澄清／回應媒體 | 「澄清115年10月30日工商時報關於本公司之報導」「應主管機關要求澄清媒體報導」 |
| 營收、自結損益 | 「本公司115年9月自結損益公告」「發布本公司115年06月份業績資料」 |
| 財務報告 | 董事會通過季報、年報 |
| 訂單、合約、合作 | 簽訂重要契約、策略聯盟、廠房租賃 |
| 新產品、認證、許可 | 「本公司異體幹細胞獲得衛生福利部外銷專用藥品許可證」 |
| 投資、資產買賣 | 取得或處分資產、投資計畫、子公司釋股 |
| 籌資 | 現金增資、可轉換公司債、私募、減資 |
| 股利、庫藏股 | 配息、買回庫藏股 |
| 人事異動 | 董事長、總經理、發言人、主管異動 |
| 股東會、董事會、法說會 | 股東會召開與決議、董事會例行決議、法人說明會 |
| 負面事件 | 訴訟、裁罰、災害、資安事件、停工、退票 |
| 其他 | 上面都不是 |

2. **標記**（可以同時成立）：
   - **更正／補充**：更正、補充、修正先前的公告。
   - **有新消息**：公告裡有新的資訊（營收數字、新訂單、新許可…），不是例行或依規定才公布的。對注意股最重要：看得出這則公告能不能解釋為什麼漲跌。
3. **白話摘要**：一句話講公告重點，例如「10 月營收 15.2 億，年增 31%」，不超過 40 字。

不做「利多／利空」判斷：太接近投資建議。

**結果是什麼**：

- 卡片的公告列：類型標籤取代官方條款的名稱，「有新消息」的公告標出來，主旨太長時顯示白話摘要。
- ③ 寫摘要時用公告類型、「有新消息」和白話摘要，不用自己讀公告全文。

## ② 新聞 RAG

**做什麼**：資料線多抓一個來源：每天收盤後，替注意股、聽牌股向 FinMind 抓當天的新聞標題。新聞標題轉成向量存進 PostgreSQL（pgvector），用向量合併重複的報導、挑出跟被注意原因最相關的幾則；③ 寫摘要時，把挑好的新聞和自己的資料（`app_card`、公告）一起交給 LLM，摘要多寫一句新聞，句尾標明出處。

**為什麼要做**：被列注意通常是漲跌或成交量異常，公告只有公司自己說的話；新聞能看出市場在討論什麼（題材、法人動向、產業消息），補上「為什麼會漲」的背景。

**結果是什麼**：

- 摘要的第三句講新聞，例如「自由時報 11/20 報導…（新聞）」，下面附用到的新聞連結；前兩句仍只用自己的資料。
- 近 7 天沒有新聞就不寫第三句，不硬湊。
- 「有新聞」「沒新聞」兩版比較的結果用來調 prompt（哪些新聞要跳過、第三句怎麼寫），不是決定要不要做。

**用向量做兩件事**（WHERE 做不到，要靠「意思相近」）：

- **合併重複的報導**：同一件事好幾家媒體都報，標題寫法不一樣（「XX 接獲 AI 伺服器大單」「XX 獲美系雲端廠訂單」），WHERE 分不出是同一件事；兩則標題的向量很接近，就只留一則。
- **挑出相關的新聞**：把「被注意的原因＋近期公告主旨」也轉成向量當查詢，跟這檔最近 7 天的新聞比相似度，留最相關的前 5 則；大盤快訊、成交量排行這類跟原因無關的分數低，自然被排掉。大型股一天幾十則時差別最明顯；小型股新聞少，主要用到的是合併重複。

向量存在同一個 PostgreSQL（pgvector），不用另外架 Chroma：新聞、向量、注意股資料在同一個資料庫，一句 SQL 就能先篩股票、日期再比相似度。

## ③ 每日卡片 AI 摘要

**做什麼**：每天收盤後，替每檔注意股、聽牌股寫 2～3 句白話摘要，顯示在卡片最上面。第一句講**為什麼被注意**，第二句講**現在走到哪**（還差幾次、處置中幾號出關）。只寫已發生、已公布的事，不寫「若再被列就哪天處置」這種推算（網頁也不放）。

**為什麼要做**：被注意的原因是法規寫法（例如「最近六個營業日累積收盤價漲幅達 32%」），款次要對照要點才知道意思；還差幾次、處置日期散在卡片各欄。一般人要的是一句話講完「發生什麼事、接下來會怎樣」。

**結果是什麼**：卡片最上面一段摘要，例如：

> 6108 今天因第一款（漲幅）被列注意，連續第 2 天，再被列 1 次就達「連續三個營業日」的處置標準（要點第六條第一項第一款）。公司 11/14 公告 10 月營收年增 31%，無未公開重大訊息。

資料由程式查好，AI 只負責寫成人話；摘要裡的數字、日期都會用程式檢查，不讓 AI 自己編。不預測漲跌、不給買賣建議。

## 串起來、上雲

- **網站**：資料 API（FastAPI）讀規則引擎的結果和 AI 項目的結果，Streamlit 網頁打 API 顯示；哪個項目還沒做或當天失敗，那一區就不顯示，其他照常。
- **排程**：Airflow 每天收盤後跑資料線、抓新聞，接著跑 ①、③；AI 失敗不影響資料線。
- **雲端**：GCP（Cloud SQL、VM 或 Cloud Run）。

## 對照 FinMind 的 AI 做法

FinMind（台股資料平台）有四種 AI 整合：給網頁版 AI 讀的 `llms.txt`、Claude Code 的指令檔（Agent Skill）、MCP server（[FinMind-MCP](https://github.com/FinMind/FinMind-MCP)，開源）、ChatGPT 的 Custom GPT。它的使用情境是讓外部使用者的 AI 查資料，跟這個專題（每天批次跑、結果存表給網站讀）不同，但有幾個做法可以借。

**整體架構**：FinMind 網站的分析結果由排程預先算好，網站只讀結果，跟這個專題一樣。它的 `knowledge/` 資料夾把資料集說明、錯誤訊息、範例寫成 markdown，MCP 和 Custom GPT 共用同一份。這個專題可以照做：之後開始做 AI 項目時新增 `knowledge/` 資料夾，規則條文和款次說明寫成一份 markdown，每個項目都讀這一份。

逐項對照：

| 項目 | FinMind 的做法 | 借到這個專題 |
| --- | --- | --- |
| ① 公告分類 | `knowledge/regression.md`：固定一組測試案例 | 人工標記 100 則當固定案例，改 prompt 後重跑比分數 |
| ② 新聞 RAG | `TaiwanStockNews` 資料集（來自 Google 新聞，有標題、連結、來源、時間） | 直接用這個資料集當新聞來源，不自己爬 |
| ③ 卡片 AI 摘要 | 指令檔的「意圖 → 資料集」對照表 | 「款次 → 白話說法」對照表，AI 照表解釋，比每次自己讀法條穩定 |
| ③ 卡片 AI 摘要 | 指令檔的輸出規則段落（格式、語言） | 固定一段輸出規則：幾句、先講什麼、數字從哪來、不給建議 |

不借的：MCP server、`llms.txt` 是給外部使用者的 AI 用的，這個專題沒有這種使用者。
