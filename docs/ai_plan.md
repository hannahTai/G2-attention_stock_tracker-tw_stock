# AI 項目

> 2026-11-16 整理，2026-11-24 更新

資料線（API → raw → stage → app）算出注意股離處置還差幾次；AI 項目在旁邊多做三件事：公告分類、新聞 RAG、卡片 AI 摘要。各自讀資料庫、各自寫結果表，哪一個當天失敗都不影響資料線和網站。

## 整體架構

```
股價線（週一～五 18:00～22:00 每小時）
  證交所 → crawler → raw_* → transform → stage_*（注意股…）→ analyze → app_*（還差幾次）
新聞線（每天 08:00 起每 3 小時，到 23:00）
  stage_watched_stock 決定查哪些公司 → 觀測站、FinMind → crawler → raw_* → transform → stage_*（重大訊息、新聞）→ AI

AI（新聞線：只讀 stage_* 和前面的 AI 結果，不讀 app_*；和股價線的 analyze 互不等）
  ① 公告分類     重大訊息 → Claude（結構化輸出）→ ai_announcement_label
  ② 新聞 RAG     新聞網頁 → Claude 寫摘要 → ai_news_summary
                 標題＋摘要 → bge-m3 轉向量 → ai_news_embedding（pgvector）
                 同一件事歸在一起 → ai_news_story
  ③ 卡片 AI 摘要 注意股的事實＋① 的公告＋② 挑出的新聞 → Claude 寫 2～3 句 → ai_card_summary

網站
  資料 API（FastAPI）讀 app_*、ai_*（透過 VIEW），網頁（FastAPI＋Jinja2）打 API
```

新聞線一輪的順序：公告分類 → 新聞摘要 → 新聞向量 → 同一件事 → 卡片 AI 摘要（後面的會用到前面的結果）。卡片 AI 摘要要用當天的注意股、處置股、收盤行情（股價線）和這檔的公告、新聞清單（新聞線），都到了才寫：股價線成功的那一輪放完記號就接著跑一次新聞線，當天的卡片在那時候寫（一檔一天一次）；往前看 7 天，補沒寫成的。

| 項目 | 做什麼 | 為什麼要做 | 新概念 |
| --- | --- | --- | --- |
| ① 公告分類 | 每則重大訊息：類型（13 類）、更正、有沒有新消息、是不是壞消息、一句白話摘要 | 用主旨關鍵字判斷錯很多；官方條款太粗（第51款什麼都有） | 結構化輸出 |
| ② 新聞 RAG | 抓 FinMind 新聞、寫摘要、轉向量；同一件事歸在一起；替卡片挑相關的新聞 | 公告只有公司自己說的話，新聞看得出市場在討論什麼 | embedding、向量檢索（pgvector） |
| ③ 卡片 AI 摘要 | 每檔注意股寫 2～3 句白話：最近漲跌多少、可能的原因 | 被注意的原因是法規寫法，一般人看不懂 | RAG 的生成 |

② 加 ③ 就是完整的 RAG：檢索（自己的資料用 SQL 查、新聞用向量找）＋生成（寫成摘要、附出處）。

## 共同原則

- **批次、存表**：排程跑（新聞線每 3 小時；卡片摘要每天收盤後一次），結果存成表給網站讀；不做聊天式問答。
- **AI 不取代規則引擎**：還差幾次、處置日期由規則引擎算；AI 的輸入也不讀規則引擎的結果（`app_*`），只讀 stage 和其他 AI 結果。
- **AI 結果放 `ai_*` 表**：`app_*` 隨時可以從 stage 免費重算；AI 結果重跑要花錢、同樣的輸入答案可能不一樣，所以拿到就留著。重算 stage、app 不碰 `ai_*`。
- **只處理新資料**：結果表的主鍵含 `prompt_version`，已經有同一版結果的跳過；改了 prompt 就加一版，新版另外存、舊的留著比較。
- **輸入沒變就不問**：卡片 AI 摘要存輸入的雜湊值，跟前一天一樣（處置中、沒有新公告、沒有新新聞）就沿用前一天的摘要。
- **有新公告就重寫**：卡片 AI 摘要記下寫的時候給了幾則公告（`announcement_count`）；寫完以後又出現新的（例如 18:00 寫好、公司 19:30 才發公告），下一輪新聞線重寫那張。
- **程式檢查 AI 的回答**：摘要裡的數字都要出現在輸入裡、引用的新聞編號要是這次給的，才算 `summary_ok`；沒過的網站不顯示。
- **記錄每次呼叫**：`ai_llm_call` 記 token、快取、花費、秒數、模型、prompt 版本、成功或失敗。
- **有就帶、沒有照寫**：卡片 AI 摘要會用公告分類和新聞 RAG 的結果，但它們當天沒有結果也照樣寫，不互相依賴（但這檔那天的新聞清單、那個月的公告清單要抓過才寫，不會寫成「沒有公告和新聞」）。
- **失敗 3 次就不再問**：同一筆、同一版 prompt 拒答、被截斷 3 次就跳過（`repository.MAX_FAILED_CALLS`），新聞線一天跑 6 次也不會一直重問；換版本重新算。新聞的網頁打不開、全文太短（沒有問 LLM）記一列「跳過」，1 天後再試（一天最多一次）。
- **看品質**：`scripts/ai_report.py` 列出最近幾天每個項目、每個版本重問幾成、失敗幾次、花多少、幾成沒通過檢查；換 prompt 版本以後跑一次，和舊版比。
- **沒設 `ANTHROPIC_API_KEY`**：跳過要呼叫 Claude 的項目，不算失敗；新聞向量、同一件事照做（不用 API）。
- **外部文字是資料、不是指令**：新聞、公告放在 prompt 的標籤裡，system prompt 說裡面的要求一律忽略；AI 只產生文字和標記，不能動其他資料。

### 用什麼

| | 選擇 | 原因 |
| --- | --- | --- |
| LLM | Claude（`claude-haiku-5-5`，三個項目各自可以在 `.env` 換：`AI_CLASSIFY_MODEL`、`AI_SUMMARY_MODEL`、`AI_CARD_MODEL`） | 小型模型便宜、夠用；結構化輸出保證回傳符合 JSON schema |
| 呼叫方式 | 直接用 Anthropic SDK，不用 LangChain、LlamaIndex | 步驟少、每一步看得到；一則問一次，system prompt 標快取 |
| embedding 模型 | bge-m3（本機跑，1024 維） | 中文效果好、免費、資料不用送出去 |
| 向量存哪 | PostgreSQL 的 pgvector | 見下面「為什麼用 pgvector，不另外架 Chroma」 |
| 佇列 | `ai`（呼叫 Claude，同時 2 個）、`embed`（要用 bge-m3 的，一次 1 個） | Claude API 有速率限制；模型約 2.3 GB 記憶體，只載入一份 |

## ① 公告分類

**為什麼要做**：原本用主旨關鍵字判斷公告類型，錯很多：

| 關鍵字規則的問題 | 例子 |
| --- | --- |
| 誤判成說明 | 「受邀參加線上法說會，說明115年第一季營運成果」：是法說會，不是事件說明 |
| 漏掉回應媒體 | 「媒體報導本公司遭彰化縣衛生局處罰新台幣600萬」：沒有「澄清」「說明」字樣 |
| 漏掉更正類 | 「（補充說明）本公司油品代製廠商…」：規則只認「更正」 |

官方的「符合條款」也幫不上忙：第51款「其他重大事項」什麼都有（注意股例行說明、澄清媒體、營收、新藥許可…）。要判斷「是不是回應媒體」「有沒有新消息」得讀懂意思，所以交給 AI。

**輸入**：每則公告的發言日期、主旨、符合條款、事實發生日、說明全文（`stage_announcement`、`stage_announcement_detail`）；全文整段給，最長的公告也只有幾千 token。

**輸出**（`ai_announcement_label`）：

| 欄位 | 內容 |
| --- | --- |
| `category` | 13 類選一個（schema 用 enum 限定，不會出現自己編的類型） |
| `is_correction` | 更正、補充、修正先前的公告 |
| `has_news` | 有新的資訊；例行、依規定才公布的為否 |
| `is_negative` | 對公司是壞消息（衰退、虧損、訴訟、裁罰…；照事實判斷，不是預測股價） |
| `summary` | 一句白話摘要，最多 60 字，數字只能用公告裡有的 |
| `reason` | 一句理由（評估、除錯用） |

13 類：

| 類型 | 例子 |
| --- | --- |
| 注意股例行說明 | 「係因本公司有價證券達公布注意交易資訊標準，故公布相關財務業務等重大訊息」 |
| 澄清／回應媒體 | 「澄清115年10月30日工商時報關於本公司之報導」 |
| 營收、自結損益 | 「本公司115年9月自結損益公告」 |
| 財務報告 | 董事會通過季報、年報 |
| 訂單、合約、合作 | 簽訂重要契約、策略聯盟、廠房租賃 |
| 新產品、認證、許可 | 「本公司異體幹細胞獲得衛生福利部外銷專用藥品許可證」 |
| 投資、資產買賣 | 取得或處分資產、投資計畫、子公司釋股 |
| 籌資 | 現金增資、可轉換公司債、私募、減資 |
| 股利、庫藏股 | 配息、買回庫藏股 |
| 人事異動 | 董事長、總經理、發言人、主管異動 |
| 股東會、董事會、法說會 | 股東會召開與決議、董事會例行決議、法人說明會 |
| 負面事件 | 訴訟、裁罰、災害、資安事件、停工、退票 |
| 其他 | 上面都不是 |

不做「利多／利空」判斷：太接近投資建議。`is_negative` 只照事實判斷。

**用在哪**：網站的公告列顯示類型、「有新消息」、白話摘要（沒通過檢查的不顯示摘要）；卡片 AI 摘要用類型和白話摘要，不用自己讀公告全文。

**摘要太長**：超過 60 字就帶著上次的回答請它縮短，只重問一次；還是太長就照存，`summary_ok`＝否。

## ② 新聞 RAG

### 新聞從哪來

FinMind 的 `TaiwanStockNews`（`https://api.finmindtrade.com/api/v4/data`）：

- 參數 `data_id`（股票代號）、`start_date`；一次只能抓一天。
- 欄位：日期時間、股票代號、連結、來源（自由時報、CMoney…）、標題。只有標題，沒有內文。
- 量：小型股一天通常 0～3 則，大型股一天幾十則；同一則新聞可能出現兩次。
- 帶 token 每小時 600 次：走 `crawl_finmind` 佇列，6 秒一個。

資料線：

```
crawl_finmind：被關注的上市公司（stage_watched_stock），一檔一天一個任務 → raw_stock_news（還沒過完的那天，30 分鐘內抓過就先不重抓）
crawl_news：打開新聞網頁，只存 <head>（標題、meta 摘要）、全文有幾個字 → raw_news_detail
transform → stage_news（一則一列，主鍵＝連結的 md5）、stage_stock_news（哪檔有哪則）、stage_news_detail（導言）
```

全文不存資料庫（著作權）。打開新聞網頁有限制：只打 http(s)、不打內部網址、只讀網頁（HTML）、最多 5 MB、60 秒內讀完、轉址最多 5 次。

### 新聞摘要

- 哪些：被關注的股票（往前 30 個交易日被列注意過，和卡片牆同一批）最近的新聞，有抓到網頁、全文至少 200 字的。
- 怎麼做：當場再打開網頁抽全文（只在記憶體裡），最多給前 6,000 字，請 Claude 用自己的話寫摘要；存的只有摘要（`ai_news_summary`）。
- 長度：文章的三成，最少 80、最多 1,200 字；太長就請它縮短一次。

### 轉成向量

- 轉什麼：**標題＋新聞摘要**；沒有摘要用導言，都沒有就只有標題。
- 模型：bge-m3，本機跑，1024 維，長度正規化成 1（cosine 相似度＝內積）。
- 存哪：`ai_news_embedding`（主鍵 `news_id`＋模型，欄位 `embedding vector(1024)`）。換模型時新的另外存一份，比較完再換。
- 只轉要轉的：文字的雜湊值和上次一樣就跳過；摘要後來才寫好的，文字變了，會重轉。

**不分段（chunking）**：轉的是標題＋摘要，摘要平均約 220 字，bge-m3 一次放得下；全文本來就不存。我們要的是「一則新聞一個向量」代表它在講什麼。分段是給長文件（財報、法規、全文）、要找到「哪一段」的時候用的。

### 同一件事（`ai_news_story`）

好幾家媒體報同一件事，歸成一個 story；網站的新聞列表一件事只列一則，旁邊寫「也有 X、Y 報導」。

一則新聞和 **3 天內、同一檔股票、比它早** 的新聞比，符合其中一個就算同一件事：

- **同一篇**：標題一樣，或一則標題是另一則的開頭（轉貼時後面加了欄目名稱；短的那則至少 10 個字）；
- **意思一樣**：向量相似度 ≥ 0.84。

找最像的那則，歸到它的 story；`story_id` 是這件事最早的那則新聞。0.84 是看實際資料定的：標題＋摘要的相似度 0.84～0.88 幾乎都是同一件事別家寫的，0.82 以下多半是不同的事。

標題文字比對抓不到「健策接獲大單」和「健策獲 AI 伺服器訂單」是同一件事，所以要比向量（意思）。

### 替卡片挑新聞（檢索）

1. 查詢＝股票名稱＋近 30 天公告的主旨和摘要，轉成一個向量。不放被注意的原因（「當日沖銷成交量占…比率61.27%」這種條文字句）：放了會去比對「股價大漲」的快訊，找不到「為什麼」。
2. 這檔最近 7 天、有向量的新聞，用 pgvector 的 cosine 距離（`<=>`）排好。
3. 拿掉沒內容的（論壇貼文、個股概覽、法人買賣超表、重複注意股名單的快訊）、相似度低於 0.45 的。
4. 同一件事只留最相關的一則，其他家記成「也有報導」；最多 5 則交給卡片 AI 摘要。

### 為什麼用 pgvector，不另外架 Chroma

這個專案的向量查詢一定是「先篩某檔股票、某段日期，再比相似度」，每次只比幾十到幾百則：

| | MySQL ＋ Chroma | PostgreSQL ＋ pgvector |
| --- | --- | --- |
| 服務 | 2 個，各自備份、監控 | 1 個 |
| 先篩條件再比相似度 | 跨兩個系統，程式自己接 | 一句 SQL：`WHERE` 股票、日期 `ORDER BY embedding <=> 查詢` |
| 資料一致 | 兩邊要自己同步 | 同一個資料庫、同一個交易 |
| 備份 | 兩套 | 一次 pg_dump |
| 向量很多時 | Chroma 專門做向量，大量時有優勢 | 先篩條件後量很小，不需要索引；要對全部找最像的可以加 HNSW 索引 |

資料庫原本規劃用 MySQL；加入新聞 RAG 時比較過，改成 PostgreSQL：向量和其他資料放一起，而且 upsert（`ON CONFLICT`）、視窗函式（算 30 日內注意幾次）也用得到。程式透過 `common/repository.py` 存取資料庫，換資料庫的改動集中在那一層。

什麼時候該用專門的向量資料庫：向量上百萬筆、查詢不先篩條件（直接在全部裡找最像的），或需要專門的向量功能時。

## ③ 卡片 AI 摘要

**做什麼**：替卡片牆上的每一張（往前 30 個交易日被列注意過的上市公司，一檔一天）寫 2～3 句白話，重點是「這檔最近為什麼漲（跌）這麼多」：

- 第一句：股價最近怎麼了（漲或跌、幅度，數字照官方寫的情況；今天被列注意的也可以用今天的漲跌幅）。
- 接著：可能的原因，只用公告（公告分類的摘要）和挑出的新聞；看不出原因就直說。
- 被列注意的原因用白話（款次換成白話說法，對照表在 `ai/card_summarizer.py` 的 `CLAUSES`）；處置中的可以帶一句背景（期間撮合變慢）。
- 今天沒被列注意的：講清楚是哪天被列注意、那天的情況（例如「11/18 被列注意時，最近六個交易日漲了 32.10%」），不說成今天。
- **不寫**第幾款、規定、離處置還差幾次：讀者在意的是為什麼漲跌；還差幾次卡片上已經有，而且是規則引擎算的。
- 不預測漲跌、不給買賣建議。

**輸入**（全部來自 stage 和其他 AI 結果，不讀 `app_*`）：那天的注意股（今天沒被列注意的，帶最近一次被列注意的日期和那天官方寫的情況）、處置期間和撮合間隔、今天的漲跌幅（今天被列注意的才給，輸入每天一樣才能沿用前一天的摘要）；近 30 天公告（含公告分類）；新聞 RAG 挑出的新聞（標題、來源、日期、新聞摘要、也有誰報導）。資料由程式查好、先寫成白話交給 Claude，Claude 只負責寫成通順的話。

**輸出**（`ai_card_summary`）：摘要、用到哪幾則新聞（`news_used`；網頁在摘要下面列出標題和連結，標題、連結從資料庫查，不用 Claude 打的字）、輸入雜湊值、模型、prompt 版本。

到 2026-11-23（`ai_llm_call` 從 2026-11-22 開始記）：

| 項目 | 結果筆數 | 呼叫次數 | 花費（美元） | 平均每次 |
| --- | --- | --- | --- | --- |
| 公告分類 | 7,472 則公告 | 10,097 | 1.75 | 0.00017 |
| 新聞摘要 | 1,848 則 | 5,312 | 1.39 | 0.00026 |
| 卡片 AI 摘要 | 263 張 | 579 | 0.11 | 0.00020 |
| 新聞向量、同一件事 | 6,288 則、4,438 件 | 不呼叫 API | 0 | 0 |

呼叫次數比結果多：改 prompt 後重跑新版本、太長請它縮短都算一次。之後每天只處理新資料。

查每天的花費：

```sql
SELECT called_at::date AS day, task, count(*) AS calls, round(sum(cost_usd)::numeric, 3) AS usd
FROM tw_stock.ai_llm_call
GROUP BY 1, 2
ORDER BY 1 DESC, 2;
```

## 還沒做

- **評估**：公告分類人工標 100 則當標準答案，算準確率、每一類的 precision、recall；新聞檢索人工標 20 檔，比較向量挑的前 5 則和「最新 5 則」；卡片 AI 摘要固定 20 檔人工評分（正確、完整、易讀）。
- **排程**：現在用 Windows 工作排程器跑兩條線（`main.py` 股價線、`main.py news` 新聞線）；之後換 Airflow（兩條線各一個 DAG、失敗通知），每一步裡的大量小任務照樣交給 Celery。
- **雲端**：GCP（Cloud SQL、VM 或 Cloud Run）；API key 用 Secret Manager。
- **花費上限**：在 Anthropic 後台設每月上限；網站加一頁看每天花費。

## 對照 FinMind 的 AI 做法

FinMind（台股資料平台）有四種 AI 整合：給網頁版 AI 讀的 `llms.txt`、Claude Code 的指令檔（Agent Skill）、MCP server（[FinMind-MCP](https://github.com/FinMind/FinMind-MCP)，開源）、ChatGPT 的 Custom GPT。它的使用情境是讓外部使用者的 AI 查資料，跟這個專題（每天批次跑、結果存表給網站讀）不同，借了這幾個做法：

| 項目 | FinMind 的做法 | 這個專題 |
| --- | --- | --- |
| 新聞 RAG | `TaiwanStockNews` 資料集（來自 Google 新聞） | 直接用這個資料集當新聞來源，不自己找新聞 |
| 卡片 AI 摘要 | 指令檔的「意圖 → 資料集」對照表 | 「款次 → 白話說法」對照表（`CLAUSES`），AI 照表解釋，不自己讀法條 |
| 卡片 AI 摘要 | 指令檔的輸出規則段落 | system prompt 固定一段輸出規則：幾句、先講什麼、數字從哪來、不給建議 |
| 整體 | 分析結果由排程預先算好，網站只讀結果 | 一樣 |

不借的：MCP server、`llms.txt` 是給外部使用者的 AI 用的，這個專題沒有這種使用者。
